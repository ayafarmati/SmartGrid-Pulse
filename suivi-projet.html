Le flux depuis le début

Le premier objectif d’Aya est de produire un relevé simulé, de l’envoyer dans GCP et de prouver où il arrive. Ce parcours comporte la création de l’infrastructure, le déploiement du programme, puis la circulation des relevés.

Préparer le passage des données

  1. Ouvrir le projet. Aya travaille dans smartgrid-pulse depuis Cloud Shell, le terminal Google Cloud. Les fichiers .tf décrivent les ressources à préparer et le fichier d’état mémorise ce que Terraform gère déjà.
  2. Créer le trajet avec Terraform. Le premier déploiement a créé le topic Pub/Sub grid-telemetry-topic, la souscription qui livre ses messages et la table BigQuery Bronze streaming_raw_events. La table conserve le message brut, son identifiant et son heure de publication.
  3. Tester le trajet à la main. Aya a publié un texte et un relevé JSON avec gcloud. Elle a retrouvé le même identifiant dans BigQuery, puis lu la puissance, la tension et la fréquence avec SQL. Ce test est validé sur GCP.
  1. Aya publie
  2. Topic Pub/Sub
  3. Souscription BigQuery
  4. Table Bronze

Installer le programme qui produira les relevés

  1. Écrire et tester le simulateur. telemetry.py génère un événement par sous-station. app.py expose la commande HTTP POST /simulate et publie les cinq événements dans Pub/Sub. Le comportement a été testé localement.
  2. Préparer sa destination. Terraform a créé Artifact Registry pour stocker les images Docker et sa-simulator, l’identité que le programme utilisera pour publier. Le nouveau dépôt et les droits sont validés sur GCP.
  3. Construire et envoyer l’image. Cette étape est validée. Docker a assemblé le code Python et ses dépendances. Artifact Registry a confirmé l’envoi de v0.1.0 avec son digest.
  4. Créer le service Cloud Run. Cette étape est validée. Terraform a relié le service au digest de l’image, attaché sa-simulator et autorisé le compte d’Aya à appeler le service.
  1. Code Python
  2. Docker build
  3. Artifact Registry
  4. Cloud Run

Suivre un relevé une fois Cloud Run en service

  1. Aya déclenche le scénario. Elle envoie une requête authentifiée à POST /simulate avec sous-frequence. Cloud Run lance le conteneur si nécessaire. Le simulateur crée cinq relevés et associe un même batch_id à tous.
  2. Le relevé traverse la chaîne. Celui de Madrid contient 49.7 Hz et le statut UNDER_FREQUENCY. Le programme le publie avec le compte sa-simulator. Pub/Sub confirme la publication avec un message_id, puis sa souscription écrit le JSON dans BigQuery.
  3. Aya et Abarkha vérifient les résultats. Aya a retrouvé les cinq stations dans BigQuery à partir du batch_id. Abarkha utilisera le relevé de Madrid pour vérifier le contrôle du seuil, puis l’alerte et sa notification dans Cloud Monitoring.

Le flux historique suit un parcours parallèle. Abarkha charge les fichiers espagnols dans Cloud Storage et prépare les données. Aya les utilise ensuite pour entraîner la prévision de demande nationale. Le flux simulé fournit les mesures des sous-stations pour la supervision.

Les trois commandes déjà exécutées

image_uri="europe-west1-docker.pkg.dev/smartgrid-pulse/smartgrid-containers/simulator:v0.1.0"

gcloud auth configure-docker europe-west1-docker.pkg.dev &&
docker build --platform linux/amd64 -t "$image_uri" ../simulator &&
docker push "$image_uri"
  1. Configurer l’accès Docker. gcloud auth configure-docker configure Docker pour utiliser l’identité de ton compte Google lorsque Docker contacte le registre de la région europe-west1.
  2. Construire l’image. docker build lit le Dockerfile dans ../simulator, installe les dépendances et construit une image Linux amd64. L’option -t attribue à l’image son adresse et le tag v0.1.0.
  3. Envoyer l’image. docker push transfère les couches de l’image et son manifeste dans le dépôt GCP. La ligne v0.1.0: digest: sha256:... confirme l’envoi. Les && lancent chaque commande seulement si la précédente réussit.

Terminal et infrastructure

Cloud Shell
Le terminal Linux ouvert dans la console Google Cloud. Il contient les fichiers du projet Terraform, Docker et la CLI gcloud. Lorsque tu es dans terraform/, ../simulator désigne le dossier voisin où se trouvent les sources et le Dockerfile.
Terraform et le provider Google
Terraform lit les fichiers .tf. Le provider traduit la configuration en opérations sur les API Google Cloud. validate vérifie la configuration, plan calcule les changements, et apply exécute le plan relu.
État Terraform
Le fichier terraform.tfstate relie les ressources écrites dans le code à celles déjà créées sur GCP. C’est pour cela que chaque nouveau plan est lancé dans le même dossier Cloud Shell. Les plans sauvegardés et l’état restent dans ce dossier de travail.
Projet, API et région
smartgrid-pulse regroupe les ressources et les permissions. Les API Artifact Registry, IAM et Cloud Run ont été activées pour permettre les opérations de création. europe-west1 est la région choisie pour le dépôt, le service à venir et le dataset BigQuery.

Code, image et registre

Python, Flask et Gunicorn
telemetry.py crée les cinq relevés et applique le scénario choisi. app.py utilise Flask pour exposer l’API. Gunicorn sert cette application HTTP dans le conteneur sur le port 8080.
Dockerfile et dépendances
Le Dockerfile décrit comment assembler l’image à partir de Python 3.12, de requirements.txt et des fichiers du simulateur. La bibliothèque Pub/Sub permet à l’application de publier les relevés. La commande de démarrage lance Gunicorn.
Image et conteneur
L’image emballe le code, les bibliothèques et la commande de démarrage. Un conteneur est une instance en cours d’exécution de cette image. docker build prépare l’image dans Cloud Shell et Cloud Run démarrera les conteneurs à partir de cette image.
GitHub et Artifact Registry
GitHub sert à versionner les sources du projet. Le Dockerfile du simulateur fait partie des nouveaux fichiers importés dans Cloud Shell. Artifact Registry conserve les images construites. Le dépôt smartgrid-containers fournira l’image au service Cloud Run.
URI, tag et digest
L’URI contient le registre régional, le projet, le dépôt et le nom simulator. Le tag v0.1.0 est une étiquette lisible. Le digest sha256:... identifie le contenu exact de l’image. Terraform utilisera l’URI avec ce digest pour déployer la version qui vient d’être envoyée.

Exécution et droits d’accès

Cloud Run
Le service managé charge l’image et exécute le conteneur lorsque le simulateur reçoit une requête. Le réglage de développement prévoit zéro instance minimale, une instance maximale et un lot de cinq événements par requête.
Requête HTTP et JSON
Une requête POST /simulate demande la création d’un lot. Le corps JSON {"scenario":"sous-frequence"} choisit l’anomalie. Le code génère cinq objets JSON avec les identifiants, l’heure UTC, les mesures et le statut.
IAM et droit d’invocation
IAM définit qui peut faire quoi. Le rôle roles/run.invoker autorisera Aya à appeler le service avec un jeton d’identité fourni par gcloud. L’appel à l’URL est soumis à cette vérification.
Compte de service et ADC
sa-simulator est l’identité de l’application pendant sa présence sur Cloud Run. La bibliothèque Google obtient automatiquement les identifiants de cette identité via Application Default Credentials. Le rôle roles/pubsub.publisher est limité au topic grid-telemetry-topic.

Livraison et preuve dans BigQuery

Topic et souscription Pub/Sub
Le topic reçoit les publications. La souscription grid-telemetry-bigquery-sub assure leur livraison vers bronze_smartgrid.streaming_raw_events. Ce trajet a été validé avec des publications manuelles.
Confirmation de publication
Le service attend les confirmations Pub/Sub avant de répondre. Elles indiquent quels messages Pub/Sub a acceptés. BigQuery reçoit les événements ensuite. La requête BigQuery apporte la preuve que le lot a effectivement été livré.
batch_id, event_id et message_id
Le batch_id regroupe les cinq relevés d’un appel. Chaque relevé a son propre event_id. Pub/Sub attribue un message_id à chaque publication. Les identifiants permettent de suivre le lot et de dédupliquer les relevés dans la requête.
Table Bronze et requête SQL
Bronze reçoit le message brut et ses métadonnées. La requête filtre la partition temporelle et le batch_id, puis extrait du JSON les colonnes station, fréquence et statut. Le résultat attendu contient cinq stations, dont Madrid à 49,7 Hz avec UNDER_FREQUENCY.

Projet et cas d’usage

Ce que construit SmartGrid Pulse

SmartGrid Pulse est une plateforme de données et de Machine Learning sur Google Cloud. Elle collecte la demande et la production électriques historiques, les prix et la météo, puis estime la demande nationale espagnole pour les 24 prochaines heures. En parallèle, elle surveille cinq sous-stations fictives à Madrid, Barcelone, Valence, Séville et Bilbao.

Le tableau de bord sert à lire les heures de pointe et la prévision de charge. L’écran de supervision sert à localiser une sous-station et à observer ses mesures de fréquence, de tension et de température.

Cas d’usage · Anticiper un pic et surveiller le réseau

  1. Avant la pointe. Une personne chargée de la planification regarde la demande prévisionnelle heure par heure. Aya construit le modèle à partir de l’historique, du calendrier et des variables météo préparées par Abarkha.
  2. Décision. Dans Looker Studio, la personne repère la prochaine heure de pointe, compare la prévision à la référence du gestionnaire et consulte l’intervalle d’incertitude pour préparer la surveillance de cette période.
  3. Pendant la supervision. Pour la démo, Aya fait émettre par le simulateur une fréquence de 49,7 Hz à Madrid. Abarkha vérifie que la valeur franchit le seuil bas de 49,8 Hz, que l’alerte est visible et que sa notification est enregistrée.
  4. Résultat attendu. Une prévision exploitable jusqu’à 24 h et une alerte traçable jusqu’au relevé simulé. Les observations des sous-stations fictives servent à la supervision et l’historique espagnol sert à l’apprentissage.

Schéma d’architecture SmartGrid Pulse

Le schéma sépare les trois couches du médaillon en colonnes. Bronze conserve les données brutes. Silver contrôle, nettoie et structure les données. Gold prépare les variables, stocke les prévisions et les anomalies, puis expose les vues destinées à Looker Studio.

Orchestration et livraison

Composer exécute le DAG dans cet ordre : arrivée GCS → ETL et qualité → variables Gold → inférence → anomalies → notification. Terraform provisionne les ressources. GitHub Actions utilise Workload Identity Federation pour valider et planifier les changements. Les images des services Cloud Run sont stockées dans Artifact Registry.

Sécurité, lignage et coûts

Prévoir une identité par service avec droits limités et colocaliser BigQuery et GCS en europe-west1. Si des données de compteurs sont retenues, pseudonymiser les identifiants dès l’ingestion et exposer uniquement les agrégats autorisés. Knowledge Catalog (Dataplex) trace les sources et transformations prises en charge. En développement, lancer Cloud Run et Spark à la demande et réserver Composer à la fenêtre de validation.

Limiter les coûts pendant le développement

  • Lancer le simulateur à la demande par lots de cinq et configurer Cloud Run avec zéro instance minimale.
  • Conserver le filtre de partition et la rétention de sept jours sur la table de test. Limiter les octets facturables des requêtes de validation.
  • Tester Spark Serverless sur un extrait avant de charger tout l’historique. Prévoir l’environnement Composer pour la fenêtre de validation.
  • Configurer des alertes de budget et contrôler la facture après les tests cloud.
